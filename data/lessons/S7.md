## Generators {#generators}

- `(expr for x in it)` is a **generator expression**, not a tuple: `type(g).__name__` is `'generator'`.
- `[expr for x in it]` builds the whole list now; a generator produces values **lazily**, one per request.
- Generators hold only their current state, so they use far less memory than the equivalent list.
- They are **single-pass**: once consumed, `list(g)` gives `[]` and `sum(g)` gives `0`.
- `print(g)` shows `<generator object <genexpr> at 0x...>`, not the values.
- No indexing, no `len()`: `g[0]` and `len(g)` raise `TypeError`.
- A `yield` anywhere in a `def` makes it a generator function: calling it runs **no** code and returns a generator.
- `yield` pauses and resumes; `return` inside a generator **ends** it (its value is not yielded).
- `x in g` consumes items up to and including the first match.
- A generator expression can be passed directly as the only argument: `sum(x * x for x in range(4))` gives 14.

```python
def countdown(n):
    print('start')
    while n > 0:
        yield n
        n -= 1

g = countdown(3)        # nothing printed yet
print(next(g))          # start / 3
print(list(g))          # [2, 1]
print(list(g))          # []  (exhausted)
```

```python
g = (n for n in range(10))
print(5 in g)           # True
print(list(g))          # [6, 7, 8, 9]
```

## Iterators {#iterators}

- An **iterable** can give an iterator (`list`, `str`, `range`, `dict`...); an **iterator** also has `__next__`.
- `iter(iterable)` returns an iterator; `next(it)` returns the next item.
- An exhausted iterator raises `StopIteration`; `next(it, default)` returns `default` instead.
- `next([1, 2])` raises `TypeError`: a list is iterable but not an iterator.
- A `for` loop calls `iter()` once, then `next()` until `StopIteration`, which it catches silently.
- An iterator keeps its position: after a `break`, the rest can still be consumed.
- Iterator protocol for your own class: `__iter__` (returns `self`) and `__next__` (returns the next value or raises `StopIteration`).
- If `__iter__` does not reset the state, the object can be traversed only once.
- A `range` can be traversed many times; `iter(range(3))` only once.
- `zip(it, it)` with the *same* iterator pairs consecutive items.

```python
class PowTwo:
    def __init__(self, max=0):
        self.max = max
    def __iter__(self):
        self.n = 0
        return self
    def __next__(self):
        if self.n > self.max:
            raise StopIteration
        self.n += 1
        return 2 ** (self.n - 1)

print(list(PowTwo(3)))       # [1, 2, 4, 8]
it = iter([1])
print(next(it), next(it, 'end'))  # 1 end
```

## Functional programming {#functional}

- `lambda args: expr` takes a **single expression** (no `return`, no assignment, no `assert`); default values are allowed. Lambdas are handy as short callbacks (p. 205).
- Lambdas capture variables, not values: `[lambda: i for i in range(3)]` all return 2 (fix: `lambda i=i: i`).
- `map(f, it)` and `filter(f, it)` return **lazy** iterator objects in Python 3: no `len()`, single pass, `f` only runs when consumed.
- `map(f, a, b)` takes one item from each iterable and stops at the shortest; so does `zip`.
- `sorted(it, key=..., reverse=...)` returns a **new list**; `lst.sort(...)` sorts in place and returns `None`.
- Sorting is **stable**: items with equal keys keep their original order.
- `max`/`min` with `key=` return the item (not the key) and the **first** one in case of a tie.
- `all([])` is `True`, `any([])` is `False`; both short-circuit.
- `functools.reduce(f, it)` folds from the left; without an initial value the first item is the starting accumulator.
- `enumerate(it, start=0)` yields `(index, item)` pairs.

```python
words = ['bb', 'a', 'cc', 'd', 'aa']
print(sorted(words, key=len))        # ['a', 'd', 'bb', 'cc', 'aa']
print(words.sort())                  # None
print(list(map(lambda x, y: x + y, [1, 2, 3], [10, 20])))  # [11, 22]
```

```python
from functools import reduce
print(reduce(lambda acc, x: acc * 10 + x, [1, 2, 3]))      # 123
print(max(['kiwi', 'banana', 'cherry'], key=len))          # banana
print(all([]), any([]))                                    # True False
```

## Assertions {#assertions}

- `assert cond, msg` does nothing if `cond` is truthy, otherwise raises `AssertionError(msg)`.
- `str(e)` of the caught exception is the message; without a message it is empty.
- The condition uses truthiness: `assert []`, `assert 0.0` fail; `assert 'False'` passes.
- `assert (cond, msg)` asserts a non-empty **tuple**: always true (CPython emits a SyntaxWarning).
- Running `python -O` removes all asserts: never rely on them to validate user input.
- Use them as sanity checks of conditions that must hold during development.

```python
def isqrt(n):
    assert n >= 0, 'n must be non-negative'
    i = 0
    while i * i < n:
        i += 1
    return i

print(isqrt(16))    # 4
isqrt(-4)           # AssertionError: n must be non-negative  (no error with python -O)
```

## Context managers {#context-managers}

- `with open(...) as f:` closes the file automatically when the block ends, even after an exception.
- It is equivalent to `try: ... finally: f.close()`.
- The name bound by `as` still exists after the block, but I/O on the closed file raises `ValueError`.
- Your own class: `__enter__(self)` runs first, its **return value** is bound by `as`; `__exit__(self, exc_type, exc, tb)` runs when the block ends.
- If `__enter__` returns nothing, the `as` variable is `None`.
- If `__exit__` returns a true value, the exception raised in the block is **suppressed**; otherwise (e.g. `None`) it propagates after `__exit__` has run.

```python
class Ctx:
    def __enter__(self):
        print('enter')
        return 'resource'
    def __exit__(self, exc_type, exc, tb):
        print('exit', exc_type)
        return True              # swallow exceptions

with Ctx() as r:
    print(r)
    1 / 0
print('after')
# enter / resource / exit <class 'ZeroDivisionError'> / after
```

## Unit testing {#testing}

- A unit test checks that a piece of code behaves as expected; `unittest` is in the standard library.
- Write a class that inherits from `unittest.TestCase`; each test is a method whose name **starts with `test`**.
- Other methods (e.g. `check_x`) are not run; tests run in **alphabetical** order of their names.
- `setUp` runs before **each** test method.
- Assertions: `assertEqual` (`==`), `assertTrue` (truthiness), `assertIs` (identity), `assertIn`, `assertGreater`, `assertRaises`...
- A failed assertion is a **failure**; any other exception raised in a test is an **error**.
- `with self.assertRaises(KeyError):` fails if the block raises nothing (e.g. `{}.get('k')`).
- `if __name__ == '__main__': unittest.main()` runs the tests of the file.
- The `coverage` package measures how much of the code is executed by at least one test.

```python
import unittest

class T(unittest.TestCase):
    def test_eq(self):
        self.assertEqual([1, 2], [1, 2])      # passes (== not is)
    def test_raises(self):
        with self.assertRaises(ZeroDivisionError):
            1 / 0                             # passes
    def helper(self):                         # not a test: never run
        self.fail()
```

## Logging and debugging {#logging-debugging}

- Prefer `logging` to `print`: severity levels, output to console or file, context (time, module, line...).
- Levels: DEBUG (10) < INFO (20) < WARNING (30) < ERROR (40) < CRITICAL (50).
- The default level is **WARNING**: `logging.debug` and `logging.info` print nothing until you lower the level.
- `logging.basicConfig(level=logging.DEBUG, format='%(levelname)s:%(message)s')` configures the root logger.
- By default log messages go to **stderr**; `stream=sys.stdout` or `filename=...` changes that.
- Arguments are merged lazily with %-formatting: `logging.info('n=%d', 3)`.
- A record must pass both the logger's level and the handler's level.
- IDE debuggers let you set **breakpoints**, step through code and inspect variables (harder for GUI/Flask apps).

```python
import logging, sys
logging.basicConfig(stream=sys.stdout, format='%(levelname)s:%(message)s')
logging.info('hidden')        # (nothing: below WARNING)
logging.warning('shown')      # WARNING:shown
logging.error('n=%d', 3)      # ERROR:n=3
```

## Command-line arguments with argparse {#argparse}

- `parser = argparse.ArgumentParser()` then `parser.add_argument('--num_iter', type=int, default=10)`.
- `args = parser.parse_args()` reads `sys.argv`; pass a list (`parse_args(['--num_iter', '34'])`) to test it.
- Both `--num_iter 34` and `--num_iter=34` are accepted.
- Values are **strings** unless `type=` converts them: without `type=int`, `args.num_iter * 2` repeats the string.
- The `default` is used when the option is absent.
- Dashes become underscores: `--learning-rate` gives `args.learning_rate`.
- Invalid values or unknown options make argparse print a usage error and raise `SystemExit`.

```python
import argparse
parser = argparse.ArgumentParser()
parser.add_argument('--num_iter', type=int, default=10)
print(parser.parse_args([]).num_iter)                  # 10
print(parser.parse_args(['--num_iter=34']).num_iter)   # 34
parser.parse_args(['--num_iter', 'ten'])               # error message + SystemExit
```

## Program efficiency {#efficiency}

- Prefer built-ins (`sum`, `max`, `min`, `sorted`...): they are implemented in C.
- Vectorize with NumPy/Pandas instead of Python loops (`np.sum(np.arange(n))`, `df['d'] / df['c']`).
- Avoid `iterrows` loops; express if/elif/else with `.loc[mask, col] = ...`, the most specific rule last.
- "Know your algebra": a loop of products and sums is `np.dot(x, m)`.
- Membership: `x in a_set` is ~O(1) (hashing), `x in a_list` is O(n).
- `multiprocessing.Pool().map(f, items)` spreads work over several CPU cores and gathers the results.
- Numba (`@numba.jit(nopython=True)`) compiles a function to machine code at run time; Cython compiles a Python superset to C.
- Use a profiler to find bottlenecks before optimizing; keep the code simple and readable.

```python
import numpy as np
x = np.array([1.0, 2.0, 3.0]); m = np.array([0.5, 0.5, 2.0])
print(np.dot(x, m), np.sum(x * m))   # 7.5 7.5
print(x * m)                         # [0.5 1.  6. ]  (element-wise, not a number)
```

## Good practices {#good-practices}

- The Zen of Python (`import this`): "Readability counts", "Explicit is better than implicit", "Flat is better than nested", "Errors should never pass silently"...
- Follow a style guide, usually **PEP 8**: `snake_case` functions/variables/modules, `CapWords` classes, `UPPER_CASE` constants.
- Docstrings for every module, class and function: summary line, details, then `Args:`, `Returns:`, `Raises:`, `Attributes:` (classes).
- A docstring is stored in `f.__doc__` (shown by `help(f)`).
- Type hints (`def f(x: int) -> float:`) are optional, for readers and tools; they are **not checked** at run time and live in `f.__annotations__`.
- Split a project into packages and modules; each package directory has an `__init__.py`.
- Run from the project root, import with `from pkg.sub import module`; keep a `README.md` and a `requirements.txt`.
- Peer review catches bugs early, enforces guidelines and spreads knowledge; version control (git) keeps the history.

```python
def double(x: int) -> int:
    """Return twice x."""
    return x * 2

print(double('ab'))        # abab  (hints are not enforced)
print(double.__doc__)      # Return twice x.
```

## Exam traps checklist {#traps}

- `(x for x in ...)` is a generator, not a tuple; printing it shows `<generator object ...>`.
- Generators, `map` and `filter` objects are single-pass: the second `list()` is `[]`, the second `sum()` is 0.
- `len()` and indexing on a generator or map object raise `TypeError`.
- Calling a generator function runs nothing until `next()`; one `yield` anywhere makes it a generator.
- `return` in a generator stops it; its value is not yielded.
- `next()` on an exhausted iterator raises `StopIteration`; `next(it, default)` does not.
- `next(list)` raises `TypeError`: call `iter()` first.
- `lambda` body = one expression: `return`, `=` or `assert` inside is a `SyntaxError`.
- `lst.sort()` returns `None`; `sorted()` returns a new list; sorting is stable.
- `max(..., key=len)` returns the first longest item, not its length.
- `all([])` is True, `any([])` is False.
- `reduce` without an initial value starts from the first item (type surprises!).
- `assert (cond, msg)` never fails; `python -O` disables every assert.
- `as` gets what `__enter__` returns; `__exit__` returning True swallows the exception.
- Reading a file after its `with` block raises `ValueError` (closed file).
- unittest runs only `test*` methods, alphabetically; a failed assert is a failure, another exception an error.
- Logging default level is WARNING: `debug`/`info` print nothing.
- argparse values are strings without `type=`; `--my-opt` becomes `args.my_opt`; bad input -> `SystemExit`.
- Type hints are never enforced at run time.
